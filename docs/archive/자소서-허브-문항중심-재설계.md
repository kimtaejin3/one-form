# 자소서 허브 — 문항 중심 재설계

작성일: 2026-07-25. 대상: `apps/backend`(essays 모델·API) + `apps/web`(자소서 허브). 이전
설계([자소서-작성-저장-허브-설계.md](자소서-작성-저장-허브-설계.md))의 **1문항-1기업 결합을 폐기**하고
문항을 독립 객체로 만드는 재설계.

## 1. 문제 (지금 왜 틀렸나)

현재 백엔드는 `essays = [{회사 + 문항}]` 평면 리스트라 **한 문항이 한 기업에 박제**된다. 그래서
같은 유형 문항이 회사마다 중복되고, 문항 자체를 다루지 못한다. 프론트도 덧붙이기(드롭다운→모달→
페이지네이션)로 IA 없이 커졌다.

## 2. 올바른 모델 (문항 ↔ 기업 = 다대다)

```
문항(Question)  독립 객체. id·유형(tag)·질문(prompt)·글자수. 답변 1개(재사용).
기업(Company)   문항들을 참조 + 자기 마감일.  삼성 → [A,B,C],  네이버 → [A,D,E]
답변(Answer)    문항 id에 붙는다(기업 무관, 재사용).  content·status
```

- **답변은 문항당 1개, 재사용**한다. A를 한 번 쓰면 A를 묻는 모든 기업에 공유된다.
- **`{회사}` 템플릿 변수**: 질문·답변에 넣으면 기업 맥락에서 그 회사명으로 치환한다.
  - 저장은 원본(토큰 포함): `"저는 {회사}의 인재상에…"`.
  - 기업 맥락(기업별에서 삼성 선택)에서 보면 `"저는 삼성전자의…"`. 맥락 없으면(문항별) `귀사`로 렌더.
- 특정 기업에 안 묶인 문항 = `companies`가 빈 문항(공통/재사용 전용).

## 3. 백엔드 (`apps/backend/app/essays/`)

### 3.1 데이터 (`repository.py`)
- `_QUESTIONS`: `[{id, tag, prompt, char_limit}]` — 유니크 문항 풀(약 10~13개). prompt에 `{회사}` 허용.
- `_COMPANIES`: `[{name, deadline, question_ids: [int]}]` — 기업→문항 참조 + 마감.
- `_ANSWERS`: `dict[int, {content, status}]` — 문항 id별 답변(재사용, in-memory).
- 조회는 문항 풀에 답변과 "이 문항을 쓰는 기업들"을 합쳐 반환.

### 3.2 스키마 (`schemas.py`) — 클래스명 전역 유일(‘Company’는 companies 도메인과 충돌하므로 피함)
- `QuestionCompany{ name: str, deadline: str }`
- `Question{ id, tag, prompt, char_limit, answer: str, status: Literal["미작성","작성 중","초안 완료"], companies: list[QuestionCompany] }`
- `AnswerUpdate{ content: str, status: Literal[...] }` (재사용)
- `DraftResponse{ question_id: int, draft: str }`

### 3.3 API (`router.py`)
- `GET /api/essays/questions` → `list[Question]` (문항 풀 + 답변 + 쓰는 기업들). 한 응답으로 두 뷰 파생.
- `PUT /api/essays/questions/{question_id}/answer` (바디 `AnswerUpdate`, `response_model=Question`) → 문항 답변 저장, 없는 id 404.
- `POST /api/essays/draft` (바디 `{question_id}`, `response_model=DraftResponse`) → 문항 초안(목).
- 기존 평면 `GET /api/essays`·`/{id}/answer`는 제거(대체).

## 4. 화면 (검색 + 2뷰, 모달·페이지네이션 없음)

```
┌──────────────────────────────────┬────────────────────┐
│ 🔍 검색   [문항별 | 기업별]   진행 ▓▓░ 3/13           │
├──────────────────────────────────┼────────────────────┤
│ 문항별: A 지원동기  ● 3개 기업     │  선택 문항 에디터   │
│         B 성장과정  ○ 2개 기업     │  질문(회사명 치환)  │
│         C 자기소개  ✓ 공통          │  답변 textarea(원본)│
│ 기업별: [삼성 ▾] → A·B·D  (D-3)   │  {회사} 삽입        │
│                                   │  미리보기(치환 결과)│
└──────────────────────────────────┴────────────────────┘
```

- **뷰 토글 [문항별 | 기업별]**:
  - **문항별**: 유니크 문항 풀. 각 행에 유형·상태·저장답변 미리보기·"N개 기업 사용"(공통이면 그렇게 표시).
    선택 시 에디터에 **기업 맥락 없음** → `{회사}`는 `귀사`로.
  - **기업별**: 회사 선택(design-system `Dropdown` 재사용) → 그 회사 문항만 + 그 회사 마감(D-day).
    선택 시 에디터에 **그 회사 맥락** → `{회사}` 치환.
- **검색**: 문항 텍스트·유형·회사명으로 현재 뷰를 좁힌다. (드롭다운·모달·페이지네이션을 대체)
- **에디터**: 답변은 **원본(토큰 포함) 편집**, 아래 **미리보기**에 현재 맥락 치환 결과. `{회사}` 삽입 버튼.
  저장·글자수 카운터·AI 초안·상태(초안 완료) 유지. 저장은 문항 id 기준(재사용).
- 진행 요약: 전체 문항 대비 완료 수(문항 기준, 재사용이라 문항당 1회 카운트).

## 5. 재사용 / 폐기

- **재사용**: design-system `Dropdown`(기업 선택), 저장 흐름(문항 id 기준으로 재배선), 진행 요약,
  글자수·상태·AI초안 로직.
- **폐기**: 평면 essays 모델, 1:1 회사 필터 탭(CompanyTabs), 문항별 모달, 페이지네이션.

## 6. FSD (프론트)

- `entities/essay`: 타입을 `Question`(gen:api)으로. `essaysQuery` → `GET /questions`.
- `features/save-answer`: 문항 id 기준 PUT으로 재배선.
- `features/generate-draft`: `question_id` 기준.
- `pages/essays`: 검색 상태·뷰 토글·기업 선택·선택 문항을 `useState`, 서버 상태는 Query, useEffect 페칭 금지.
  `{회사}` 치환은 렌더 중 순수 함수로. 500줄 넘으면 분리.

## 7. 테스트

- **pytest**: `GET /questions`(문항 풀 + companies 합류·answer 기본 ""), 저장→반영·404·status 422,
  draft shape. 기업→문항 매핑이 응답에 반영되는지.
- **vitest**: 문항별↔기업별 토글, 검색 좁힘, 기업 선택 시 그 회사 문항만, `{회사}` 치환(맥락 있음=회사명,
  없음=귀사), 저장→미리보기·완료율 갱신, 글자수 초과.

## 8. 범위 밖 (노트)

- AI 초안이 문항을 실제 반영(RAG/LLM) — 여전히 목. `{회사}` 치환은 프론트 표시 레벨(생성 아님).
- 사용자가 직접 문항/기업 추가(CRUD 생성) — 추후.
- 실제 DB·인증 — in-memory 목 유지.

## 9. 구현 순서 (DAG)

1. **backend-dev**: 모델(문항 풀·기업 매핑·답변) + 스키마 + `GET /questions`·`PUT .../answer`·draft,
   `pnpm gen:api`, pytest.
2. **web-dev** (deps 1): entities/features 재배선 + 검색·2뷰 토글·기업 Dropdown·`{회사}` 치환 에디터,
   폐기 대상 제거(CompanyTabs·모달·페이지네이션), vitest. (design-system도 web-dev 담당)
3. **qa** (deps 2): lint·test·build·드리프트·요구 UX·회귀 검증.
4. QA 통과 → 워크트리 In Review → 사용자 확인 → 머지.
