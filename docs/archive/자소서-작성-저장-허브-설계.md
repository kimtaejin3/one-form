# 자소서 작성·저장 허브 설계

작성일: 2026-07-25. 대상: `apps/web`(자소서 허브 UI) + `apps/backend`(essays 저장 API).
관련: [IA.md](IA.md) §4.3 자소서 허브, 현행 essays 목 구현.

## 1. 목표

자소서 허브를 "문항 하나씩 보는 화면"에서 **전체 문항을 한눈에 훑고 · 회사별로 걸러 보고 · 각 문항에
쓴 답을 저장·재열람하는 작업 공간**으로 확장한다.

핵심 요구(사용자 확정):
- **회사에 묶이지 않은 전체 질문 리스트가 기본**으로 보인다.
- 상단 **회사 필터**로 특정 회사 문항만 좁혀 볼 수 있다.
- 각 문항에 **저장된 답변 미리보기 + 상태**가 붙어 "어떻게 적었는지 한눈에" 파악된다.
- 답변을 **백엔드에 저장**해 새로고침·재방문에도 유지된다.

## 2. 현재 상태와 문제

현행(직전 재구조, master-detail):
- 백엔드: `Essay{id, company, tag, question, char_limit, deadline, status}`,
  `GET /api/essays → list[Essay]`, `POST /api/essays/draft → {essay_id, draft}`(목, essay_id 무시,
  `response_model` 없음).
- 프론트: `entities/essay`(타입·essaysQuery), `features/generate-draft`(초안 mutation·`EssayEditor`),
  `pages/essays`(`CompanyTabs` + `EssayListItem` + `EssayEditor`). 작성 본문은 **메모리(useState)에만** 존재.

문제:
- 회사를 **하나 골라야** 문항이 보인다 → "전체 문항 한눈에"가 안 됨.
- 작성 본문이 **저장되지 않아** 새로고침 시 소실.
- 문항 목록에 **내가 쓴 내용**이 안 드러남(상태 뱃지만).
- `/draft` 응답에 `response_model`이 없어 프론트가 `Draft` 타입을 **손으로 씀**(CLAUDE.md 규칙 위반).

## 3. UX / 레이아웃

```
┌───────────────────────────┬──────────────────────┐
│ 진행: 12개 중 3 완료  ← 전체 완료율 요약           │
├───────────────────────────┼──────────────────────┤
│ [전체] [삼성전자] [네이버] [토스] …  ← 회사 필터   │
│ ─────────────────────────  │                      │
│ 삼성전자 · 지원동기      ○  │   선택 문항 에디터    │
│ 삼성전자 · 성장과정      ○  │   질문 전문           │
│ 네이버 · 경험  ● "작년 교내…"│  ┌────────────────┐ │
│ 토스 · 역량             ○  │  │ 저장답변 로드/편집│ │
│ 쿠팡 · 포부             ○  │  └────────────────┘ │
│ … (전체 문항, 마감 임박순)  │  320/700자 [초안][저장]│
└───────────────────────────┴──────────────────────┘
```

- **좌측 리스트**: 기본은 **전체 문항**(회사 무관, 마감 임박순). 각 행 = `회사 · 문항유형` + 상태 뱃지 +
  **저장답변 첫 줄 미리보기**(없으면 "미작성"). 선택 항목 강조.
- **회사 필터**: `[전체]`(기본) + 회사별 칩/탭. 선택 시 그 회사 문항만.
- **우측 에디터**: 선택 문항의 질문 전문 + 저장답변을 로드한 편집 `textarea` + 글자 수 카운터
  (현재/`char_limit`, 초과 시 경고) + `[AI 초안 생성]` + **`[저장]`**.
- **상단 요약**: 전체 대비 완료 수(예: "12개 중 3 완료").

상태 흐름: 저장 시 `status`를 갱신(빈 답 → "미작성", 저장 시 "작성 중", 사용자가 "초안 완료"로 표시 가능).

## 4. 백엔드 (저장 — 핵심 변경)

### 4.1 스키마 (`apps/backend/app/essays/schemas.py`)
- `Essay`에 **`answer: str = ""`**(저장 본문) 추가.
- `status`를 자유 문자열 → **`Literal["미작성", "작성 중", "초안 완료"]`**로 제약(직전 QA가 지적한 자유
  문자열 취약성 해소). 클래스명 전역 유일 규칙 유지.
- 신규 `AnswerUpdate{content: str, status: Literal[...]}` (PUT 바디).
- 신규 `DraftResponse{essay_id: int, draft: str}` (draft 응답 정석화, #9).

### 4.2 엔드포인트 (`apps/backend/app/essays/router.py`)
- **`PUT /api/essays/{essay_id}/answer`** — 바디 `AnswerUpdate`, `response_model=Essay`.
  저장 후 갱신된 `Essay` 반환. 없는 id면 404.
- `POST /api/essays/draft` — `response_model=DraftResponse` 지정(#9).

### 4.3 저장소 (`apps/backend/app/essays/repository.py`)
- 모듈-레벨 **in-memory** `_ANSWERS: dict[int, dict]`(문항 id → `{answer, status}`). 기존 목 패턴과 일관.
- `list_essays()`: `_ESSAYS`에 `_ANSWERS`를 병합(저장된 answer/status로 override)해 반환.
- `save_answer(essay_id, content, status)`: 유효 id 검증(없으면 예외→404), `_ANSWERS` 갱신, 병합된
  `Essay` 반환.
- ⚠️ **제약**: in-memory라 서버 재시작 시 소실. 진짜 영구는 DB가 필요 — "mock→실제" 전략대로, DB 도입 시
  이 저장소만 실제 쿼리로 교체(router/schemas 불변). 단일 목 사용자 가정(인증·다중 사용자 없음).

## 5. 프론트 (FSD)

- `entities/essay/model.ts`: `Essay` 타입에 `answer`·status literal이 **gen:api로 자동 반영**(손수정 없음).
- **`features/save-answer`** 신설: `useSaveAnswer` (`useMutation`, PUT). `onSuccess`에서 `essaysQuery`
  invalidate → 리스트 미리보기·완료율 갱신.
- `features/generate-draft`: 유지. `Draft` 타입을 **손으로 쓴 것 제거**하고
  `components['schemas']['DraftResponse']`에서 소비.
- `pages/essays` 재구성(레이어 경계 유지, 페이지는 조합만):
  - 회사 필터(`[전체]` 포함하도록 `CompanyFilter` — 기존 `CompanyTabs` 확장/대체).
  - 전체/필터된 문항 리스트(`EssayListItem`에 저장답변 미리보기 추가).
  - 진행 요약 컴포넌트.
  - `EssayEditor` 재사용 + 저장 버튼 배선.
  - 상태: 선택 문항 id·필터 회사는 `useState`, 서버 상태는 Query. 편집 본문은 에디터 로컬 상태에서
    저장 시 mutation. (리스트가 커지면 리스트+필터를 `widgets/essay-nav`로 승격 가능 — 지금은 page ui로.)

## 6. 데이터 흐름

1. 진입: `essaysQuery`(GET) → `answer`·`status` 포함 목록. 리스트·완료율 렌더.
2. 문항 선택 → 에디터가 `essay.answer`를 로드.
3. 편집(로컬 상태) → `[저장]` → `useSaveAnswer` PUT → `onSuccess` invalidate → 리스트/요약 갱신.
4. `[AI 초안 생성]` → `generate-draft` mutation → 에디터 `textarea`에 주입(저장 전까지는 미저장).
   (초안이 문항을 반영 못 하는 백엔드 한계는 범위 밖.)

## 7. 테스트

- **pytest** (`apps/backend/tests/`): 저장 엔드포인트(저장→`GET`에 answer·status 반영), 없는 id→404,
  draft `response_model` shape(200 + `essay_id`·`draft`).
- **vitest** (`apps/web`): 회사 필터 전체/특정 전환 시 리스트 변화, 문항 선택 시 저장답변 로드,
  저장 mutation 성공 → 미리보기·완료율 갱신(fetch 목), 글자 수 초과 경고, "미작성" vs 저장됨 미리보기.

## 8. 범위 밖 / 향후

- 🔴 AI 초안이 문항을 반영 못 함(`generate_draft`가 essay_id 무시) — RAG/LLM 붙일 자리. 이번엔 목 그대로.
- 실제 DB·인증·다중 사용자 — in-memory 목으로 대체, 추후.

## 9. 구현 순서 (오케스트레이션 DAG)

1. **backend-dev**: 스키마(`answer`·status Literal·`AnswerUpdate`·`DraftResponse`), `PUT .../answer` +
   draft `response_model`, repository 저장소·병합, `pnpm gen:api`, pytest.
2. **web-dev** (deps 1): 백엔드 브랜치 병합 → 전체 리스트+회사 필터(전체 포함)·저장답변 미리보기·진행 요약,
   `save-answer` feature, 손수정 `Draft` 타입 제거, 저장 배선, vitest.
3. **qa** (deps 2): lint·test·build·드리프트·요구 UX 항목·회귀 검증.
4. QA 통과 → 워크트리를 Orca 보드 **In Review**로 이동 → 사용자 확인 → 머지.
