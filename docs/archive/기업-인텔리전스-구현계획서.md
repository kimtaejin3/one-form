# 기업 인텔리전스 구현계획서

> 목적: 이 문서 전체를 Claude Code에 전달해 구현 작업의 기준으로 사용한다.
> 대상 경로: `/companies` 기업 인텔리전스
> 작성일: 2026-08-01

## 1. 구현 목표

사용자가 기업명 또는 채용공고를 입력하면, 출처가 표시된 기업·직무 브리핑을 만들고 사용자의 마스터 프로필과 연결한다.

최종 사용자 흐름은 다음과 같다.

1. 기업명 검색 또는 채용공고 URL 입력
2. 공식 홈페이지·공식 채용 페이지·DART·공식 뉴스룸 등 신뢰 가능한 출처 수집
3. 사업, 제품, 최근 변화, 채용 직무(JD), 핵심 역량을 구조화
4. 내 프로필의 프로젝트·경력·스킬과 기업 과제를 매칭
5. 근거 링크가 붙은 기업 브리핑, 강점 매칭, 면접 질문, 자소서 활용 포인트 확인
6. 사용자가 기업을 저장하고 이후 자소서·공고 추천에서 재사용

핵심 원칙은 “그럴듯한 기업 설명 생성”이 아니라 “근거가 있는 최신 정보의 구조화”다. 출처가 없거나 확인되지 않은 내용은 생성하지 않고 `확인 필요`로 표시한다.

## 2. 현재 코드베이스와 문제점

현재 구현은 다음의 목 API다.

- 백엔드: `apps/backend/app/companies/repository.py`
- 스키마: `apps/backend/app/companies/schemas.py`
- 라우터: `apps/backend/app/companies/router.py`
- 프론트: `apps/web/src/pages/companies/ui/CompaniesPage.tsx`
- 분석 폼/결과: `apps/web/src/features/analyze-company/`
- AI 추상화: `apps/backend/app/ai/llm.py`
- 프로필 조회: `apps/backend/app/profile/`
- 공고 수집기: `apps/backend/app/jobs/sources/`

현재 문제:

- 입력 기업명과 무관하게 쿠팡 중심의 고정 결과가 반환된다.
- `source`가 실제 URL이 아닌 문자열이며 인용 가능한 원문이 없다.
- 기업 분석 결과를 저장하지 않아 매번 다시 생성한다.
- 기업·직무·출처·신호가 별도 엔티티로 분리되어 있지 않다.
- 최신성, 출처 신뢰도, 분석 실패/부분 성공 상태가 없다.
- 실제 사용자 프로필과의 매칭이 목 문자열에 의존한다.
- 기업 인텔리전스와 공고/자소서 허브 사이의 연결이 없다.

## 3. 범위

### 3.1 이번 구현에 포함

- 기업 검색 및 기업 분석 요청
- 공식/신뢰 출처 기반 수집 파이프라인
- 기업 기본 정보, 사업 영역, 제품/서비스, 최근 신호
- 채용공고 또는 JD 분석
- 출처·발행일·수집일·신뢰도 표시
- 마스터 프로필과 기업 과제/JD 역량 매칭
- 분석 결과 캐시 및 수동 새로고침
- 기업 저장/최근 분석 목록
- 기존 `/companies` UI를 정보 대시보드로 개편
- 백엔드 단위 테스트, API 테스트, 프론트 컴포넌트 테스트

### 3.2 이번 구현에서 제외

- 로그인별 영구 즐겨찾기(인증 도메인이 준비된 뒤 연결)
- 무제한 웹 크롤링 및 검색엔진 결과의 무단 저장
- 유료 데이터 제공업체 연동
- 기업 재무 전망·투자 조언·합격 확률처럼 오해 가능한 판단
- AI가 출처 없이 기업 사실을 보충하는 기능
- 자소서 자동 생성 자체(기존 essays 도메인의 후속 작업)

## 4. 권장 아키텍처

기존 `companies` 도메인 안에서 다음 계층을 분리한다.

```text
companies/
├── router.py              # HTTP 입출력만 담당
├── schemas.py             # API DTO와 상태/신뢰도 타입
├── service.py              # 분석 오케스트레이션, 캐시 정책
├── repository.py          # DB 조회·저장
├── models.py              # 기업/출처/신호/JD 모델
├── sources/
│   ├── base.py             # SourceProvider Protocol
│   ├── official.py         # 기업 홈페이지·채용 페이지
│   ├── dart.py             # DART 공시(키가 없으면 비활성)
│   ├── newsroom.py         # 공식 뉴스룸/RSS
│   └── manual.py           # 사용자가 입력한 URL/PDF
├── extraction.py           # HTML/PDF 정제·본문 추출
├── analysis.py             # LLM 구조화 출력 + 근거 검증
└── matching.py             # profile/JD/기업 과제 매칭
```

원칙:

- 라우터에서 크롤링·LLM·프로필 매칭을 직접 호출하지 않는다.
- 외부 수집기는 `SourceDocument` 형태로 통일한다.
- LLM 출력은 Pydantic 스키마로 검증하고, 모든 사실 항목은 `evidence_ids`를 가져야 한다.
- 수집 실패와 분석 실패를 전체 실패로 만들지 말고 단계별 상태로 반환한다.
- `app.ai.llm`의 공급자 추상화를 재사용하고 API 키 없는 환경에서는 deterministic mock을 사용한다.
- 프론트 타입은 수동 작성하지 않고 OpenAPI 생성 타입을 사용한다.

## 5. 데이터 모델

Alembic 마이그레이션을 추가한다. 기존 `jobs`, `profile`, `essays` 테이블은 변경하지 않는다.

### 5.1 company_intelligence

```text
id                 uuid/int PK
name               text not null
normalized_name    text unique not null
domain             text
summary            text
stage              text
business_areas     jsonb
products           jsonb
status             enum(queued, collecting, analyzing, ready, partial, failed)
last_analyzed_at   timestamptz
created_at         timestamptz
updated_at         timestamptz
```

### 5.2 intelligence_source

```text
id                 uuid/int PK
company_id         FK
kind               enum(official_site, careers, dart, newsroom, job_posting, user_url)
url                text not null
title              text
publisher          text
published_at       timestamptz nullable
fetched_at         timestamptz
content_hash       text
trust_level        enum(primary, secondary, user_provided)
raw_text           text/jsonb  # 개인정보·불필요한 HTML은 저장하지 않음
```

### 5.3 intelligence_signal

```text
id                 uuid/int PK
company_id         FK
source_id          FK
label              text
detail             text
signal_type        enum(business, product, hiring, technology, risk, culture)
confidence         numeric(0..1)
evidence_quote     text nullable
valid_until        timestamptz nullable
```

### 5.4 intelligence_job

```text
id                 uuid/int PK
company_id         FK
source_id          FK
title              text
role_category      text
location           text
employment         text
deadline           date nullable
description        text
requirements       jsonb
preferred          jsonb
core_skills        jsonb
problem_types      jsonb
```

### 5.5 intelligence_match

프로필 ID가 생기는 현재 구조를 우선 고려해 `profile_id`를 nullable로 둔다.

```text
id                 uuid/int PK
company_id         FK
job_id             FK nullable
profile_id         FK nullable
company_need       text
profile_evidence   text
match_type         enum(strength, gap, question)
score              numeric(0..100)
reason             text
source_ids         jsonb
created_at         timestamptz
```

저장 시 개인 답변이나 프로필 원문 전체를 복제하지 말고, 매칭 결과와 참조 ID만 저장한다.

## 6. 수집·분석 파이프라인

### 6.1 입력 정규화

- 기업명 공백/법인 접미사 정리
- `삼성전자`, `삼성전자(주)`를 동일한 `normalized_name`으로 처리
- URL 입력이면 도메인·공고 URL을 직접 출처로 등록
- 검색 결과를 사용할 때는 허용 도메인 목록을 우선 적용

### 6.2 출처 우선순위

1. 기업 공식 홈페이지/공식 채용 페이지
2. DART 공시
3. 기업 공식 뉴스룸/IR/기술 블로그
4. 사용자가 입력한 채용공고 URL 또는 PDF
5. 보조 매체·채용 플랫폼

보조 출처만 있는 내용은 `secondary`로 표시하고, 공식 출처가 없으면 확정 표현을 쓰지 않는다.

### 6.3 문서 추출

- HTML: 본문/제목/발행일/출처 URL 추출
- PDF: 기존 PDF 추출 유틸리티 재사용, 페이지 번호 보존
- 공고: 제목, 접수 기간, 직무, 자격, 우대, 업무, 자소서 문항을 분리
- 중복 문서는 `content_hash`로 제거
- robots.txt, 이용약관, 요청 간격, 최대 문서 크기를 준수

### 6.4 구조화 분석

LLM에 원문을 그대로 넘기지 말고, 정제된 문서와 문서 ID를 함께 전달한다. 출력은 다음을 만족해야 한다.

- `summary`, `business_areas`, `products`, `signals`, `core_skills` 구조화
- 각 항목에 `source_id` 배열 필수
- 원문에 없는 사실은 `null` 또는 `unknown`
- 신뢰도 낮은 문장은 저장하지 않고 `needs_review`로 반환
- 모델 응답 JSON을 Pydantic으로 검증

### 6.5 프로필 매칭

초기 버전은 임베딩 없이 설명 가능한 규칙/키워드 매칭으로 시작한다.

- 프로필의 프로젝트·경력·스킬을 evidence 단위로 평탄화
- JD `core_skills`와 경험 스택/하이라이트를 정규화
- 일치 근거와 부족한 역량을 별도로 생성
- 점수만 보여주지 말고 `기업 요구 → 내 경험 → 근거`를 함께 표시
- 이후 `app.ai.embedder`를 사용한 semantic score를 추가하되 기존 규칙 점수와 분리

## 7. API 설계

기존 `POST /api/companies/analyze`는 호환용으로 유지하되 새 서비스로 위임한다.

```text
POST /api/companies/analyze
body: { name: string, job_url?: string, force_refresh?: boolean }
response: CompanyIntelligence

GET /api/companies/{normalized_name}
response: CompanyIntelligence

POST /api/companies/{normalized_name}/refresh
response: AnalysisJobStatus

GET /api/companies/{normalized_name}/sources
response: list[SourceSummary]

GET /api/companies/{normalized_name}/jobs
response: list[CompanyJob]

GET /api/companies/{normalized_name}/matches
query: job_id?, profile_id?
response: list[CompanyMatch]
```

### 응답 원칙

- `status=partial`이면 `warnings`와 실패한 source provider를 포함
- `last_analyzed_at`, `fresh_until`, `source_count`를 반환
- 모든 `Signal`, `CompanyJob`, `CompanyMatch`에 `sources` 또는 `source_ids`를 포함
- 존재하지 않는 기업은 404가 아니라 분석 가능한 요청이면 `queued`로 생성
- 동일 기업 동시 분석은 idempotency key 또는 DB lock으로 중복 실행 방지

## 8. 프론트엔드 화면

현재 `AnalyzeCompany`를 다음 위젯으로 분리한다.

```text
pages/companies/ui/CompaniesPage.tsx
widgets/company-intelligence/
├── CompanySearchForm
├── CompanyOverviewCard
├── SignalTimeline
├── JobInsightList
├── MatchBoard
├── SourceDrawer
└── AnalysisStatus
```

### 화면 구성

- 상단: 기업명/공고 URL 검색, 최근 분석 기업, 새로고침
- 개요: 기업명·도메인·요약·분석 시각·신뢰도·출처 수
- 탭 1 `사업/제품`: 사업 영역과 제품, 출처 칩
- 탭 2 `최근 신호`: 채용·사업·기술·리스크 타임라인, 발행일
- 탭 3 `직무 분석`: 공고 선택, 핵심 역량 3~5개, 문제 유형, 요구/우대
- 탭 4 `내 경험 매칭`: 강점·갭·근거 프로젝트, 점수보다 설명 우선
- 하단: 출처 목록과 원문 링크

프론트 요구사항:

- 로딩/부분 성공/실패/빈 상태를 구분
- 분석 중 이전 결과를 유지하고 진행 상태만 갱신
- 외부 링크는 새 탭으로 열고 출처 도메인을 표시
- `dangerouslySetInnerHTML` 금지
- 생성 API 타입을 사용하고 수동 schema 타입을 만들지 않음
- 기존 디자인 시스템 `Card`, `Input`, `Button`, `Dropdown` 재사용

## 9. 단계별 구현 순서

### Phase 0 — 계약과 테스트 고정

- 현재 `CompanyBrief` 사용처와 OpenAPI 생성 흐름 확인
- 새 DTO 초안 작성
- 목 provider로 정상/부분 성공/실패 fixture 작성
- 기존 `/companies/analyze` 테스트 보존

완료 기준: 외부 네트워크 없이 API 테스트가 실행된다.

### Phase 1 — 저장 가능한 기업 인텔리전스 MVP

- models + Alembic migration
- repository/service 분리
- 기업명 정규화 및 캐시
- 공식 URL/manual URL provider
- 출처·신호·기본 기업 요약 저장
- `GET`, `POST analyze`, `POST refresh` API
- 기존 프론트 결과를 새 DTO에 맞춰 호환

완료 기준: 같은 기업 재조회 시 캐시를 사용하고, 각 사실에 출처 링크가 표시된다.

### Phase 2 — 공고/JD 분석

- 기존 `jobs` 데이터와 company 연결
- URL/PDF JD 추출
- 요구사항/우대사항/핵심 스킬/문제 유형 구조화
- 기업별 공고 목록 및 직무 선택 UI

완료 기준: 한 기업에 여러 직무 공고를 저장하고, 직무별 핵심 역량이 달라진다.

### Phase 3 — 프로필 매칭

- profile repository에서 프로젝트·경력·스킬 evidence 추출
- 규칙 기반 strength/gap 매칭
- 매칭 근거와 참조 ID 저장
- `MatchBoard` UI 및 자소서 허브 연결 버튼

완료 기준: 목 문자열이 아닌 사용자의 실제 마스터 프로필 데이터가 매칭 결과에 반영된다.

### Phase 4 — 신뢰도·최신성·운영 안정화

- source trust level, freshness, content hash
- provider별 rate limit/timeout/retry
- 분석 비용·호출량 로깅
- 실패 문서 재처리와 수동 재분석
- 오래된 결과 경고 및 출처 변경 감지

완료 기준: 일부 provider 장애가 전체 화면을 깨지 않고, 오래된 정보가 명확히 표시된다.

### Phase 5 — 임베딩/RAG 고도화

- `app.ai.embedder`로 source/JD/profile evidence 임베딩
- 검색 결과와 LLM 결과를 분리 저장
- semantic match를 규칙 점수와 함께 제공
- 인용 가능한 chunk와 페이지/문단 위치 보존

완료 기준: 모든 AI 주장에 원문 chunk와 source URL이 연결되고, 재현 가능한 분석이 가능하다.

## 10. 테스트 계획

### 백엔드

- 기업명 정규화 및 동일 기업 캐시
- provider 정상/timeout/빈 문서/잘못된 HTML
- LLM 잘못된 JSON 및 출처 없는 항목 거부
- 부분 성공 상태와 warnings
- refresh 중복 실행 방지
- JD 추출 및 핵심 역량 구조화
- 프로필 매칭 근거·score 범위
- 기존 analyze API 회귀

### 프론트

- 기업 검색 제출 및 로딩 상태
- 기존 분석 결과 유지 중 refresh
- 탭 전환 및 공고 선택
- 출처 링크/출처 drawer 렌더링
- partial/failed/empty 상태
- 매칭 결과의 강점·갭·근거 표시

외부 사이트를 테스트에서 직접 호출하지 않는다. provider 경계에서 fixture/mock을 주입한다.

## 11. 보안·비용·법적 주의

- API 키, 원문 문서, 개인 프로필은 로그에 남기지 않는다.
- 외부 사이트는 robots.txt와 이용약관을 확인하고, 공식 API/RSS를 우선한다.
- 요청 빈도·timeout·최대 응답 크기를 제한한다.
- 기업 정보는 투자·법률·채용 합격을 보장하는 조언이 아니라 출처 기반 참고 정보임을 UI에 표시한다.
- 사용자 업로드 문서와 기업 원문을 같은 프롬프트에 넣을 때 prompt injection 방어 문구와 원문 경계를 명확히 한다.
- 분석 결과에는 생성 시각과 출처 최신성을 항상 표시한다.

## 12. Claude Code 실행 지시문

```text
이 저장소의 AGENTS.md와 docs/기업-인텔리전스-구현계획서.md를 먼저 읽고 구현해라.

작업 규칙:
1. 먼저 현재 companies/jobs/profile/ai 코드와 테스트를 읽고 영향 범위를 요약한다.
```
