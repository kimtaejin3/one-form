# 채용공고 상세페이지 + 상세 목 데이터 설계

작성일: 2026-07-26. 대상: `apps/backend`(jobs 상세·목 보강) + `apps/web`(상세페이지). 선행:
[채용공고 매칭 LLM/임베딩](채용공고-매칭-LLM임베딩-설계.md).

## 1. 목표

채용공고 **상세페이지**(`/jobs/:id`)를 추가하고, 목 공고에 **현실감 있는 상세 정보**(주요 업무·자격
요건·우대·회사 정보)를 채운다. 상세 JD가 풍부해져 **임베딩·LLM 매칭이 공고별로 진짜 구분**되고,
상세페이지는 **매칭률 + 내 프로필 대비 매칭 분석**을 보여준다.

## 2. 목 데이터 재정비

- **지역 '서울' 고정 + (회사×직무) 중복 제거.** 현재 지역 라운드로빈으로 같은 (회사,직무)가 여러 번
  뜬다(카카오 프론트 52% ×3). → 유니크 (회사×직무), 전부 `서울`. 100건 → ~40건.
- **아키타입 상세(웹 서칭 기반, verbatim 복사 금지).** 리서치가 모은 공개 정보로:
  - **회사 프로필**(~20): 사업·기술스택·문화 요약.
  - **직무 JD 템플릿**(8 직무): 주요 업무·자격 요건·우대 스킬.
  - backend가 (회사×직무)로 **조합** → 각 공고 상세. **요구 스킬을 직무·회사별로 다르게** 짜 매칭이 구분되게.
- 시드는 리서치 산출물(`docs/job-seed-data.md` 또는 데이터 모듈)로 두고 backend가 로드.

## 3. 백엔드 (`apps/backend/app/jobs/`)

- **schemas** (클래스명 전역 유일):
  - `Job`(카드) 유지(+`match_rate`).
  - `MatchAnalysis{ matched_skills: list[str], missing_skills: list[str] }` — 프로필 스택 ∩ 요구 스킬 / 요구−보유.
  - `JobDetail{ …Job 필드…, description: str, responsibilities: list[str], requirements: list[str], preferred: list[str], company_info: str, match_reason: str, match_analysis: MatchAnalysis }`.
- **router**: `GET /api/jobs/{job_id}` → `response_model=JobDetail`. 없는 id 404. `/api/jobs` 피드 유지.
- **repository/service**:
  - 목을 유니크 (회사×직무)·서울로 재생성, 시드 상세 결합.
  - 매칭 파이프라인의 `_job_text`를 **상세(주요업무·요건 포함)** 로 확장 → 임베딩 구분력↑.
  - 상세 조회 시 프로필 대비 `MatchAnalysis`(충족/부족 스킬) 계산 + 기존 매칭률·근거.
- 프로필 게이트 유지.

## 4. 프론트 (`apps/web`)

- **라우트** `/jobs/:id` 추가(react-router). `JobCard`를 상세로 링크(카드 클릭).
- **상세페이지** `pages/job-detail`:
  - 헤더: 회사·직무·서울·D-day·출처 + **매칭률 뱃지**.
  - **매칭 분석**(핵심): 매칭률 + 근거 + **요구 스킬 충족(✓)/부족(○)** 리스트.
  - 주요 업무 / 자격 요건 / 우대 사항 / 회사 정보 섹션.
- `entities/job/api.ts`에 `jobDetailQuery(id)` (`GET /api/jobs/{id}`), 페이지에서 `useSuspenseQuery`.
- 타입 손수정 금지(gen:api). AsyncBoundary로 로딩·에러.

## 5. 리서치 (웹 서칭)

- 대상: 목 `_COMPANIES`의 ~20개 회사(네이버·카카오·토스…) 공개 정보(사업·스택·문화) + 8개 직무의 전형적
  업무·요구/우대 스킬. **실 공고 verbatim 복사 금지 — 공개 정보 기반 현실적 생성.**
- 산출: 구조화 시드(`docs/job-seed-data.md`), backend가 조합에 사용. 요구 스킬은 조합마다 다르게(매칭 구분).

## 6. 테스트

- **pytest**: `GET /api/jobs/{id}` 상세 shape·404, `MatchAnalysis`(프로필 스택 겹침 반영), 목 dedup(유니크 회사×직무·전부 서울), 피드 계약(match_rate)·게이트 회귀.
- **vitest**: 상세페이지 렌더(섹션·매칭 분석 충족/부족), 카드→상세 링크.

## 7. 범위 밖 (노트)

- 실 채용 API·실 임베딩/LLM 키(선행 설계의 어댑터로 키 준비 시). 지금은 목.
- 지원하기·북마크 등 상세페이지 액션 — 이후.

## 8. DAG

리서치(웹 서칭 → 시드) → backend(dedup·상세 schema·`/jobs/{id}`·MatchAnalysis·`_job_text` 확장·pytest·gen:api)
→ web(상세페이지·라우트·매칭 분석 UI·vitest) → qa. 단일 워크트리 순차. QA 통과 → In Review → 확인 → 머지.
